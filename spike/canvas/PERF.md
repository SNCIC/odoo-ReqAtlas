### 1.2 被测对象

1. **适配层**（Node，无浏览器）：`projectBundle(bundle, { layout })` → nodes / edges / lanes。
   - `layout: 'view_layout'`：使用 fixture 提供的 `viewLayout` 坐标（缺失处回退自动布局）。
   - `layout: 'auto'`：完全程序化泳道布局（按 flow 层级排序）。
2. **页面渲染**（浏览器）：React Flow 12.12.0 渲染上述投影结果。

### 1.3 浏览器压力模式（诚实声明）

页面通过 `?bench=1&scale=<n>&mode=<m>&duration=<ms>` 自动执行，结果经
`window.__canvasPerfReport` 回传（见 `scripts/browser-perf.ts`）。

| mode       | 含义                                                          | 是否是真实人类输入 |
| ---------- | ------------------------------------------------------------- | ------------------ |
| `idle`     | 只渲染，无交互                                                | 是（空转）         |
| `pan`      | 每帧 `setViewport` 仅振荡 `x/y`（`zoom` 固定 1）              | **否，合成压力**   |
| `pan-zoom` | 每帧 `setViewport` 同时振荡 `x/y` 与 `zoom`（触发重新栅格化） | **否，合成压力**   |

- 帧率由 `requestAnimationFrame` 逐帧打点，取帧间隔 P50/P95；丢弃首帧。
- 长任务由 `PerformanceObserver('longtask')`（>50 ms）统计。
- 内存取 `performance.memory.usedJSHeapSize`（仅 Chromium 提供）。
- 每个配置**单次运行 5 s**；P50/P95 为**单次运行内分布**，未做多次重复的方差研究。

### 2.1 适配层瓶颈分析

- **布局（level 计算 + 泳道分组）占投影总耗时的 ~80–90%**，是对后端的唯一热点。
- 布局耗时**超线性**：×15→×30（对象数 2×）时布局 P50 由 1.65–1.70 ms → 5.84–6.03 ms（**≈3.5×**）。
  根因是两处对规模敏感的朴素实现（见 `src/adapter.ts`）：
  1. `computeLevels` 对 flow 边做最长路径松弛，最坏 O(V·E)；
  2. `computeAutoPositions` / `computeLanes` 对每个泳道过滤全部节点，O(L·N)。
     修复方向（未在本 Spike 实施，属 M3 优化项）：邻接表 + Kahn 拓扑一次求解、泳道分组用单次
     `Map` 桶化替代表过滤。
- 即便如此，**990 对象的适配层开销（<10 ms）仍小于一帧预算**，因此 M0 结论明确：
  **不必为适配层做性能优化；优化资源应投向渲染层。**

### 3.1 规模曲线（FPS 均值）

```
FPS（均值）
60 |  ●  ●  ●        ← ×1：idle / pan / pan-zoom 全部满载 60.0
49 |              ●  ← ×30 idle = 49.4（挂载后稳态；均值被挂载期长任务拉低）
39 |        ●        ← ×6 pan = 39.1
14 |        ○        ← ×6 pan-zoom = 14.4
 8 |                  ●  ← ×15 pan = 7.9
 3 |                  ○  ← ×15 pan-zoom = 3.4
 2 |                            ●  ← ×30 pan = 2.1
 1 |                            ○  ← ×30 pan-zoom = 0.9
   +--------------------------------------------
        ×1(33)     ×6(198)    ×15(495)   ×30(990)
```

### 3.2 pan vs pan-zoom（分离「变换」与「重新栅格化」成本）

同一规模下 `pan-zoom` 明显比 `pan` 更差，说明**缩放触发的重新栅格化**是额外成本：

| 规模 |              pan P95 |              pan-zoom P95 |               比值 |
| ---- | -------------------: | ------------------------: | -----------------: |
| ×6   |              33.4 ms |                  133.4 ms |              3.99× |
| ×15  |             166.7 ms |                  566.7 ms |              3.40× |
| ×30  | 566.7 ms (P50 533.3) | 1949.9 ms (P50 1116.6 ms) | 3.44×（P50 2.09×） |

但两者在 ×15 起**都已不可用**，说明瓶颈不只是栅格化，而是**大 DOM/SVG 子树的整体
重排/重绘成本本身**。

### 3.3 内存

used heap 随规模近似线性：9.5 → 15.4 → 31.6 → 42.6 MB。
每个配置的 `memoryBefore.usedMb === memoryAfter.usedMb`，5 s 窗口内**未观察到增长**——
但窗口过短，**不足以判定无泄漏**（标注为未验证）。

### 3.4 结论与建议阈值

| 节点规模 | 实测表现（合成视口压力）                    | 建议                                                   |
| -------- | ------------------------------------------- | ------------------------------------------------------ |
| ≤ 150    | 平移 ≥ 40 FPS                               | 直接渲染，无需处理                                     |
| 150–250  | 平移 ≈39 FPS / 缩放 ≈14 FPS（缩放明显卡顿） | 基础优化：`memo` 节点组件、`onlyRenderVisibleElements` |
| 250–500  | 平移 ≈8 FPS / 缩放 ≈3 FPS（不可用）         | **必须**虚拟化 + 缩小时降级（简化边、省略标签）        |
| > 500    | 平移 ≈2 FPS / 缩放 ≈0.9 FPS                 | 分片/层级细节（LOD）、服务端预布局 + 增量渲染          |

**M0 建议性能阈值（待总指挥确认）**：

- 「流畅」：≤ **200 对象 / ≤ 350 关系**（对应 ≈39 FPS 平移）。
- 「可接受」：≤ **250 对象**。
- 触发虚拟化的硬阈值：**> 300 对象**。
- 真实 gold 样本（33 对象）仅占「流畅」阈值的 ~16%，M0/M1/M2 阶段**无需画布性能投入**。

> 注：以上阈值来自 headless 合成压力，**未在真实 GPU 桌面浏览器复核**。建议在目标设备表
> （M0-01）确定后，用同一脚本（`pnpm perf:browser`）在真实设备上重跑一次再冻结阈值。

## 4. 复现步骤

```powershell
# 1) Node 侧适配层（无需浏览器）
pnpm --filter @reqatlas/spike-canvas perf
#    → 打印 P50/P95 表格，并写出 spike/canvas/perf/adapter-results.json

# 2) 浏览器侧（需先构建 + 下载 chromium）
pnpm --filter @reqatlas/spike-canvas build
pnpm --filter @reqatlas/spike-canvas exec playwright install chromium
pnpm --filter @reqatlas/spike-canvas perf:browser
#    可选环境变量：BENCH_SCALE / BENCH_MODE(idle|pan|pan-zoom) / BENCH_DURATION / BENCH_OUT
```

人工复核（无自动化时）：`pnpm --filter @reqatlas/spike-canvas dev` → 打开页面 →
在「性能探测」面板点击「空转 3s」/「平移压力 5s」/「缩放压力 5s」，读取 FPS 与长任务。
本报告全部数字均由自动化脚本产生，**未使用人工观测数字**。
