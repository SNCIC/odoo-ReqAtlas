## 2. 上下文（Context）

实施方案 §2.1 与开发方案 §2.2 将运行时基线定为 **Node.js 22 LTS + pnpm workspace**，
并要求通过 `.nvmrc` + `package.json#engines` 双重约束锁定（§2.4）。

本次 ADR 编制在同一台开发机上实测了运行时环境，结果与基线和部分里程碑假设存在偏差：

| 项 | 基线要求 | 本机实测 | 偏差 |
| --- | --- | --- | --- |
| Node.js | 22.x LTS | v25.2.1 | 非 LTS，主版本超出基线 |
| pnpm | 9.x（候选） | 10.32.1 | 主版本高于候选 |
| npm（随 Node） | — | 11.6.2 | 仅记录，无基线约束 |
| Docker / Docker Compose | M1 起为开发栈基础 | 命令不可用（未安装） | 容器栈无法在本机验证 |
| git | — | 2.54.0.windows.1 | 满足使用 |
| OS | — | Windows（win32） | 与团队其他成员环境可能不同 |

实测命令与输出（PowerShell）：

```text
> node -v
v25.2.1
> pnpm -v
10.32.1
> npx --version
11.6.2
> docker --version
docker : 无法将"docker"项识别为 cmdlet、函数、脚本文件或可运行程序的名称。...
> git --version
git version 2.54.0.windows.1
```

问题：若不在本机约束 Node 版本，本机验证结论可能与 Node 22 LTS 基线不一致；
若不显式声明 Docker 不可用，会造成"里程碑已在本地通过"的误判。

## 3. 决策（Decision）

1. 运行时基线**维持 Node 22 LTS**（不因本机为 Node 25 而改基线）。
2. 用三重约束锁定版本：
   - `.nvmrc` 固定为 `22`；
   - `package.json#engines` 写 `"node": ">=22"`；
   - CI 使用 Node 22 运行构建、类型检查与测试。
3. 本地开发**必须**通过 `.nvmrc`（`nvm use` / `fnm use`）切到 Node 22 后再执行安装与验证；
   在 Node 25 上得到的结论视为**待复验**，不作为冻结依据。
4. pnpm 版本以 lockfile 为准；本机 10.32.1 与候选 9.x 的差异由 `packageManager` 字段统一，
   安装后校验 `pnpm-lock.yaml` 无意外漂移。
5. **Docker 相关里程碑在本机不可验证**，明确标记为未验证（见第 7 节置信度限制）。

> 注：本 ADR 仅记录偏差与处置，不修改任何根目录配置文件（`.nvmrc` / `package.json` /
> CI 配置的实际写入归属其它工作流，见第 6 节"待办"）。

## 4. 理由（Rationale）

- Node 25 非 LTS，上游依赖（Vite / Nest / Drizzle / R3F / Keycloak 客户端）的兼容矩阵
  是按 LTS 维护的，用非 LTS 验证会放大"只在本地能跑"的风险。
- 版本约束写进仓库文件（而非口头约定）才能被 CI 与新人一致复现（§2.4 双重约束）。
- 如实区分"实测通过的结论"与"未验证的结论"是交付证据的基本要求。

## 5. 后果（Consequences）

### 正面

- 基线单一：CI、开发者、试用环境均锁定 Node 22，减少环境漂移。
- 明确区分已验证与未验证项，避免误判里程碑状态。

### 负面

- 开发者需额外切换 Node 版本，本机 Node 25 无法直接用于基线验证。
- Docker 缺失使容器栈相关任务只能依赖 CI 或其它环境完成。

### 风险

- 本地在 Node 25 上通过的结论被误当作 Node 22 LTS 结论采纳。
  对策：所有"本地验证"标注宿主 Node 版本，Node 22 复验前不冻结。
- 无 Docker 导致契约/集成测试覆盖不足。对策：集成测试在具备容器的 CI 环境执行。

## 6. 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 直接把基线改为 Node 25 | 非 LTS，不满足§2.1"不追最新版"；破坏兼容矩阵 |
| 不约束 Node 版本，各用各的 | 环境漂移，CI 与本地结果不一致，不可复现 |
| 放宽 `engines.node` 为任意版本 | 失去约束意义，无法在安装期阻断 |
| 在本机用 Node 25 结论直接冻结阈值 | 与基线不符，结论不可迁移到 LTS |
| 忽略 Docker 缺失、口头假定容器栈可用 | 会造成里程碑虚假通过 |

## 7. 置信度限制（必须随结论一并引用）

1. **Node 版本**：本机在 **Node v25.2.1（非 LTS）** 上验证通过的任何结论，
   **不能完全等同于 Node 22 LTS 上的结论**；在 Node 22 复验前，相关结论标记为"待复验"。
2. **pnpm**：本机为 pnpm **10.32.1**，与候选 9.x 存在主版本差；lockfile 行为差异需在
   CI（统一 pnpm 版本）中复验。
3. **Docker**：本机 **Docker / Docker Compose 不可用**，因此
   **M1-02（Compose 栈）、M1-03（OIDC/BFF 登录）、M1-05（Drizzle 迁移与 seed）**
   等依赖容器栈的里程碑**未验证**，不得凭本机结果判定通过。
4. **操作系统**：本机为 Windows，路径分隔符、行尾、脚本行为与 Linux CI 可能不同，
   脚本需保持平台无关。

## 8. 验证方式

1. 版本一致性检查（在 Node 22 环境）：`node -v` 输出 `v22.x`；
   `node -p "require('./package.json').engines.node"` 输出 `>=22`；
   `.nvmrc` 内容为 `22`。
2. CI 门禁：CI 使用 Node 22 运行 format / lint / typecheck / unit / migration 全部通过。
3. 安装期阻断：`.nvmrc` 与 `engines` 生效后，在 Node 25 上安装应给出引擎告警/阻断
   （视包管理器严格程度而定，需实测确认，此为待验证项）。
4. 容器栈验证：在具备 Docker 的环境执行 `pnpm dev:stack`，M1-02 / M1-03 / M1-05
   相应验收点全绿。

## 9. 重新评估触发条件

- 项目正式升级运行时基线（例如 Node 24 LTS 成为新的目标并完成兼容矩阵验证）。
- CI 平台无法提供指定 Node LTS 版本。
- 依赖链出现仅 Node 25 可用、Node 22 无法满足的情况。
- 团队统一迁移到具备 Docker 且 Node 版本受控的标准开发环境，偏差消失。
