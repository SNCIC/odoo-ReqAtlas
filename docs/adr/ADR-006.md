## 2. 上下文（Context）

多人协作需要在语义层面避免"最后写入覆盖"、需要把状态变更实时推送给已连接客户端。
但系统的并发冲突对象是**结构化业务对象**（对象、关系、状态、确认），不是纯文本编辑，
冲突具备领域语义（可由领域规则判定），并非需要字符级合并。

上游 §2.2 裁定"协作使用乐观锁 + revision；首版不上 CRDT / Yjs"。需要把该裁定细化为
并发控制协议与实时通道。

## 3. 决策（Decision）

1. **乐观锁并发控制**：所有语义写必须携带 `If-Match: "rev-{n}"`；
   应用 ChangeSet 时对 `project_revision` 行加锁，`base_seq` 不匹配返回
   `409 REVISION_CONFLICT`。
2. **幂等**：POST / 命令必须携带 `Idempotency-Key`；重复键且请求体不同返回
   `409 IDEMPOTENCY_MISMATCH`，相同则返回原结果。
3. **实时推送用 SSE**：事件类型含 `project.revision.created`、`agent.run.updated`、
   `document.job.updated`、`file.updated`、`review.updated`、`notification.created`；
   SSE 必须鉴权、支持重连游标与事件去重。
4. **首版不上 CRDT / Yjs**，不做字段级自动合并；冲突显式暴露给用户并提供可解释对话框。
5. Redis 只做队列、锁、短期缓存与 SSE fan-out，**不存事实**。

## 4. 理由（Rationale）

- 业务对象冲突有领域语义，可被服务端规则判定，比字符级合并更安全且可解释。
- `If-Match` + revision 使冲突显式失败，符合 §2.2 决策 3（不用"最后写入覆盖"）。
- SSE 实现简单、方向单一（服务端 → 客户端），满足状态推送；无需双向协议。
- 不上 CRDT 减少复杂度，避免为未证明的高频并发编辑引入额外模型（§2.3）。

## 5. 后果（Consequences）

### 正面

- 冲突可解释：用户看到基于哪个 revision 的差异与推荐动作。
- 实时状态可重连补取，断线不丢事件语义。
- 并发协议与版本链（ADR-002）直接复用，无额外模型。

### 负面

- 用户需处理冲突对话框，体验不如自动合并顺滑。
- 高频并发编辑（多人同时改同一对象）会频繁产生冲突，未做自动缓解。
- SSE 为单向通道，客户端到服务端的实时协作需另走命令接口。

### 风险

- 真实并发编辑频繁阻塞（对应 §2.3 的重新评估触发）。对策：先观测冲突频率，
  达到阈值再评估 CRDT。
- SSE 连接在弱网下频繁断连。对策：重连游标 + 事件去重 + 幂等，保证补取不重复。

## 6. 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| Yjs / CRDT | 业务对象冲突非纯文本合并，引入即增加模型复杂度（§2.3） |
| "最后写入覆盖" | 静默丢失修改，冲突不可解释（违反 §2.2 决策 3） |
| 悲观锁（长事务锁定对象） | 阻塞长时编辑，多人场景体验差 |
| WebSocket 双向实时 | 首版无双向实时需求，运维与鉴权成本更高 |
| 轮询代替 SSE | 延迟高、服务端压力大，无重连游标语义 |

## 7. 验证方式

1. 冲突测试（M2-08）：两个基于同一 `base_seq` 的写入，第二个返回 `409 REVISION_CONFLICT`。
2. 幂等测试：重复 `Idempotency-Key` 行为符合契约（相同返回原结果，不同返回 mismatch）。
3. SSE 测试（M6-06）：断线后按游标重连可补取；重复事件被去重；未鉴权连接被拒绝。
4. 实时查询失效测试：收到 `project.revision.created` 后相关查询被正确失效。
5. 并发压测：k6 模拟多客户端并发写入，验证无静默数据丢失。

## 8. 重新评估触发条件

- 真实并发编辑频繁阻塞，用户反复遭遇冲突。
- 出现离线编辑后合并的强需求，乐观锁无法表达。
- SSE 在目标网络环境不可靠，或需要服务端 → 客户端的低延迟双向交互。
- 冲突频率与合并成本实测超过引入 CRDT 的成本。
