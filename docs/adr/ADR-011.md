# ADR-011：构建链路与依赖注入元数据策略

## 2. 上下文（Context）

当前工程底座在"构建链路"与"NestJS 依赖注入（DI）元数据"之间存在一处**尚未暴露但即将
致命**的不一致。实测事实（本 ADR 编制时逐项核对）：

| # | 事实 | 证据定位 |
| --- | --- | --- |
| 1 | 根 `tsconfig.base.json` 仅 `"experimentalDecorators": true`，**未启用 `emitDecoratorMetadata`**，且 `"noEmit": true` | `tsconfig.base.json` 第 23、24 行 |
| 2 | `apps/api` scripts 仅有 `dev`（`tsx watch src/main.ts`）、`typecheck`、`lint`、`test`，**无 `build`** | `apps/api/package.json` 第 7~12 行 |
| 3 | `apps/worker` 同样无 `build`；各 `packages/*` 亦无 `build`。根 `build` 为 `pnpm -r run build`，故当前生产构建**只覆盖 `apps/web`** | 根 `package.json` 第 13 行；`apps/worker/package.json`、`packages/*/package.json` |
| 4 | 开发与测试经 esbuild 系（`tsx` / `vitest`）；esbuild **不支持 `emitDecoratorMetadata`**，不发 `design:paramtypes` | `apps/api` devDependencies（`tsx`、`vitest`） |
| 5 | NestJS 构造器注入依赖 `reflect-metadata` 写出的 `design:paramtypes`；当前所有 provider 无构造器依赖，故问题未暴露 | `apps/api/src/app.module.ts`（无 provider）、`main.ts` / `create-test-app.ts` 均 `import 'reflect-metadata'` |

`docs/engineering/README.md`「已知偏差」第 3 条已记录该问题，结论为"后续里程碑引入构造器
注入时需改用 SWC 转译或显式 token，**待验证**"。

风险机制：M2 必然引入**带构造器注入**的 service（例如注入 repository / 配置 / 队列）。
在 esbuild 下运行时，`design:paramtypes` 为空，Nest 会把依赖解析为 `undefined` 或直接报
无法解析。**该失败可能静默**——编译期与启动期不报错，直到首次调用该依赖的方法才崩，
测试若只用 `app.inject()` 健康检查路径也可能漏测。

影响面：实施方案 §8.3 规定 "`main` 始终可启动"。**在 `apps/api` 具备可用于生产的生产构建
之前，M1 不得判定为可启动**——这不是代码风格问题，而是部署路径缺失的阻断项。

## 3. 决策（Decision）

### 3.1 建议默认

**采用候选 (a)：`apps/api` 生产构建走 `tsc`（开启 `emitDecoratorMetadata`），测试侧对所有
provider 一律显式 `@Inject(TOKEN)`。** 并把 (c) 的核心（全局显式 `@Inject`）作为**与构建
方案无关的通用约束立刻生效**，使测试路径不依赖任何元数据。

### 3.2 三个候选处置及其后果与代价

| 候选 | 做法 | 后果 | 代价 |
| --- | --- | --- | --- |
| (a) tsc 生产构建 + 测试显式 `@Inject` | 新增 `apps/api/build`：`tsc -p tsconfig.build.json`（`noEmit:false`、`emitDecoratorMetadata:true`、`outDir`）；生产以编译 JS 启动；测试仍走 vitest，provider 一律显式 `@Inject` | 生产路径元数据完整，DI 可靠；测试路径不依赖元数据 | 需维护 `tsconfig.build.json`（覆盖 base 的 `noEmit`/模块解析）；生产与测试转译器不同，需靠"显式 @Inject"规则抹平语义差 |
| (b) 统一换 SWC | 引入 `@swc/core`（`legacyDecorator` + `decoratorMetadata`），替换 `tsx`/`vitest` 的转译链 | 开发、测试、生产同一条转译路径，元数据一致 | 新增原生依赖与配置面；`vitest`/`tsx` 集成需额外配置；偏离 NestJS 官方默认路径；私有部署需多装 `@swc/core` |
| (c) 全局显式 `@Inject`，完全不依赖元数据 | 每处构造器参数显式标注 token；不做（或不依赖）`emitDecoratorMetadata` | 与转译器完全解耦，最稳；任何路径行为一致 | 遗漏一处即静默 `undefined`，**缺乏编译期强制**；不解决 (2)/(3) 的"无生产构建"阻断项 |

### 3.3 立即生效的约束

1. **所有 Nest provider 构造器参数一律显式 `@Inject(TOKEN)`**，禁止依赖隐式元数据注入；
   新增 provider 由代码复核把关（对应 §3.3 编码规范）。
2. `apps/api` 新增 `build` 脚本与 `tsconfig.build.json`，产出可 `node` 启动的 JavaScript；
   在此之前 M1 **不得判定为"可启动"**。
3. 生产与测试的转译差异由约束 1 消除，不通过引入 SWC 来"补齐"测试期元数据。

## 4. 理由（Rationale）

- **(a) 最贴近 NestJS 官方路径**：官方 DI 默认由 `tsc` + `emitDecoratorMetadata` 支持，
  生产构建用 `tsc` 无需新增依赖，符合 §2.1"不追最新版、依赖少"与私有部署友好。
- **测试与生产语义差异被"显式 @Inject"规则抹平**：这正是候选 (c) 的价值；把它作为跨方案
  的通用约束后，(a) 的两个路径行为一致，且不再存在静默失败空间。
- **(b) 的收益不成立**：它让测试期也能用隐式注入，但隐式注入本身不透明、易静默失败，
  不是希望保留的能力；为它引入 `@swc/core` 与第二条构建链不划算。
- **(c) 单独使用不解决阻断项**：它不产生生产构建路径，(2)/(3) 的"`pnpm build` 跳过 `apps/api`"
  仍然存在；故 (c) 适合作约束，(a) 才是处置。
- **阻断性明确**：§8.3 要求 `main` 始终可启动，而当前根本没有 `apps/api` 的生产构建，
  必须由本 ADR 显式标记为里程碑阻断。

## 5. 后果（Consequences）

### 正面

- 生产构建路径存在且与 NestJS 官方 DI 行为一致。
- 测试路径不依赖元数据，`tsx` / `vitest` 下行为可预期、可回归。
- 不新增构建依赖，CI 与私有部署更简单。

### 负面

- 生产与测试使用不同转译器（tsc vs esbuild），是长期的隐性复杂度；靠"显式 @Inject"规则
  维持一致，需持续复核。
- 需维护 `tsconfig.build.json`；`tsconfig.base.json` 的 `moduleResolution: "Bundler"` 与
  `noEmit: true` 需在 build 配置中覆盖（见第 8 节假设）。

### 风险

- 新 provider 忘记显式 `@Inject`，在 esbuild 下静默注入 `undefined`。对策：代码复核 +
  探针测试（第 7 节）纳入 CI。
- CI 只跑测试不跑生产构建，导致构建回归漏检。对策：CI 增加 `pnpm --filter @reqatlas/api build`。

## 6. 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| (b) 统一换 SWC | 新增原生依赖与第二套转译配置；其唯一收益（测试期隐式注入）本身不可取；偏离官方路径 |
| (c) 仅全局显式 `@Inject`，不做生产构建 | 不解决 `pnpm build` 跳过 `apps/api` 的阻断项；且遗漏即静默失败，无编译期强制 |
| 维持现状（不处置） | M2 引入构造器注入后必然静默失败；违反 §8.3"main 始终可启动" |
| 在 esbuild/tsx 上补齐 `emitDecoratorMetadata` | esbuild 不支持该能力，无可行实现 |
| 引入 `emitDecoratorMetadata` 后仍只用 `tsx` 跑生产 | 生产用 `tsx` 解释执行 TypeScript，私有部署与启动性能不可接受，且无稳定产物 |

## 7. 验证方式

> 探针由 `apps/api` 归属方在 M1 落地；本 ADR 定义步骤与判据。**以下命令为待执行的验收
> 步骤，本 ADR 编制时未运行**（涉及 `apps/api`，不在 ADR 工作流写入范围）。

### 7.1 探针设计

在 `apps/api/src/di-probe/` 下新增（仅作验证，验证后可移除）：

- `LeafService`（`@Injectable()`，无构造器依赖）。
- `ImplicitConsumer`：`@Injectable()`，构造器 `constructor(private readonly leaf: LeafService) {}`，**不写 `@Inject`**（依赖元数据）。
- `ExplicitConsumer`：`@Injectable()`，构造器 `constructor(@Inject(LeafService) private readonly leaf: LeafService) {}`。
- `probe.ts`：bootstrap 一个含上述 provider 的模块，打印两个 consumer 的 `leaf` 是否为 `undefined`。

### 7.2 三条路径分别运行

| 路径 | 命令 | 预期 |
| --- | --- | --- |
| tsx（开发，esbuild） | `pnpm --filter @reqatlas/api exec tsx src/di-probe/probe.ts` | `ExplicitConsumer.leaf` 为对象；`ImplicitConsumer.leaf` 为 `undefined` 或 Nest 报无法解析依赖 |
| vitest（esbuild） | 新增 `apps/api/src/di-probe/di-probe.spec.ts` 断言两者注入情况；`pnpm --filter @reqatlas/api test` | 显式通过、隐式失败 —— 证明 DI 依赖元数据 |
| tsc（生产，`emitDecoratorMetadata`） | 见 7.3 | 两者**均**注入成功 |

### 7.3 tsc 路径

1. 新增 `apps/api/tsconfig.build.json`：`extends` 根 `tsconfig.base.json`，覆盖
   `"noEmit": false`、`"emitDecoratorMetadata": true`、`"outDir": "dist"`、
   `"rootDir": "src"`，并按需覆盖 `module` / `moduleResolution`（见第 8 节假设）。
2. `pnpm --filter @reqatlas/api exec tsc -p tsconfig.build.json`
3. `node apps/api/dist/di-probe/probe.js`
4. 预期：`ExplicitConsumer` 与 `ImplicitConsumer` 均注入成功。

### 7.4 判据

- 若 tsc 路径下 `ImplicitConsumer` 成功、esbuild 路径下失败 → 证实 (a) 的
  "生产靠 tsc，测试必须显式 `@Inject`"。
- **反证门禁**：显式 `@Inject` 版本必须在三条路径**全部成功**；否则不得作为过渡规则。
- **阻断验收**：`pnpm --filter @reqatlas/api build` 退出码为 0 且产出可 `node` 启动的入口；
  在此之前，M1 判"可启动"不成立。
- CI 增加门禁：`pnpm --filter @reqatlas/api build` 加入 M1-07 CI 步骤。

## 8. 重新评估触发条件

- SWC 生态与 `vitest` / `tsx` 集成显著成熟，且团队认为"单一转译链"的价值超过新增依赖成本。
- `tsc` 生产构建在真实代码规模下出现无法接受的构建耗时或产物问题。
- NestJS 官方对 DI 元数据策略做出改变（例如默认不再依赖 `emitDecoratorMetadata`）。
- 出现只能用隐式注入表达的框架能力，而显式 `@Inject` 无法覆盖。
