# ADR-002：事实与版本

| 项目 | 内容 |

## 2. 上下文（Context）

系统需要"唯一事实源"，且事实必须**可追溯、可差异、可回滚、不可被普通编辑覆盖**。
现实约束：2D 画布、Agent、导入、模板实例化都会产生写入；若各自直接写业务表，
事实源会被污染（P1、P2）。

上游 §2.2 裁定语义写入使用 `If-Match: "rev-{n}"` + `Idempotency-Key`，基线不可原地修改。
需要一套统一的写入与版本链模型，明确**谁写、写什么、如何留痕、如何冻结**。

## 3. 决策（Decision）

1. 统一语义对象以 `model_object` / `model_relation` 为唯一事实主链；
   其他模块（2D、3D、文档、Agent 草案）**只读** Snapshot 或经 API 访问，不得另存业务表。
2. 所有语义写入**只能经 Command / ChangeSet 服务**进入：
   - `change_set`：写入凭证，记录 `base_seq`（提交时的 `project_revision`）、
     `status`、`actor`、`reason`、`source`。
   - `change_operation`：单条操作，记录 `op`、`target_type/id/temp_id`、`before`、
     `after`、`source_refs`、`reason`、`confidence_state`。
3. 应用规则顺序固定：Schema → 权限 → `If-Match` → 幂等键 → tempId 解析 →
   **单事务**全量应用；任一阻断规则失败**整体回滚**，不允许半成功。
4. `project_revision` 为项目级单调版本号；语义写入成功即 `revision + 1`。
5. `snapshot`：由 `revision_seq` 序列化产出，写入对象存储后计算 `sha256`，
   与元数据同事务登记，**创建后不可变**。
6. `baseline`：同一范围仅一个当前基线，批准后只能通过变更分支更新；
   基线对象普通编辑被拒绝，只允许标记废止并记录替代对象。
7. `confirmation` 绑定 `object_id + object_rev`；对象语义修改使 `object_rev` 变化后，
   旧确认保留历史但**不再有效**，界面回到"待确认"并通知。
8. 服务端自行补齐并保存 `before` 值；客户端提供的 `before` 仅用于冲突提示。

## 4. 理由（Rationale）

- 唯一写入入口是"事实源不被污染"的结构性保证（P1 + P2）。
- 变更集天然提供差异、审计与逐项审阅能力，满足回滚与恢复需求。
- 版本号 + `If-Match` 使并发冲突显式失败，避免"最后写入覆盖"（P4 事实与推断分离）。
- Snapshot 不可变 + 哈希使文档与 3D 有一致的只读依据（§2.2 决策 6）。

## 5. 后果（Consequences）

### 正面

- 全链路可追溯：任一事实可回溯到 ChangeSet、操作者与来源。
- 差异草案、逐项接受/拒绝、基线冻结在同一模型下统一实现。
- 同一 revision 重复生成 Snapshot 内容哈希一致，可做一致性校验。

### 负面

- 所有写入都要经 Command 服务，简单保存也需走完整校验链，开发与性能成本上升。
- Operation 结构较抽象，前端需维护 tempId 到真实 ID 的映射。
- 布局拖动等高频操作需要与语义写入分离，实现更复杂。

### 风险

- 规则数量膨胀拖慢进度（风险在 §6.3 已识别）。对策：首版严格按开发方案附录 C 的
  12 条规则实现，新增走变更单。
- 事务内校验与服务端补齐 `before` 易出现遗漏。对策：集成测试覆盖回滚与并发场景。

## 6. 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 各模块直接写业务表 | 破坏唯一事实源，无法统一审计与回滚（违反 P1、P2） |
| "最后写入覆盖"并发模型 | 静默丢失他人修改，冲突不可解释 |
| 事件溯源（全量 event log 作事实源） | 查询与迁移复杂度高，首版无证据需要 |
| 数据库触发器做校验 | 规则分散在 DB 与应用两处，难测试、难版本化 |
| 基线对象原地可编辑 | 破坏批准边界，文档与 3D 无法锁定一致快照 |

## 7. 验证方式

1. 单测：`pnpm test` 覆盖 12 条领域规则，每条有稳定 error code。
2. 并发测试：两个基于同一 `base_seq` 的 ChangeSet，第二个必须返回
   `409 REVISION_CONFLICT`。
3. 幂等测试：同 `Idempotency-Key` 重复提交相同体返回原结果；不同体返回
   `409 IDEMPOTENCY_MISMATCH`。
4. 回滚测试：注入一条阻断规则失败，验证库中不残留半成功对象。
5. 快照测试：同一 revision 重复生成 Snapshot，校验 `sha256` 一致且创建后不可修改。
6. 确认失效测试：修改已确认对象的语义，验证其确认状态回到"待确认"。

## 8. 重新评估触发条件

- 12 条规则不足以表达真实业务，频繁需要例外。
- 单事务应用在真实数据规模下产生不可接受的锁等待。
- 出现必须保留完整历史事件流的合规或分析需求。
- Snapshot 哈希在合法场景下不稳定（序列化不确定性）。
