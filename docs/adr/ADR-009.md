# ADR-009：检索

| 项目 | 内容 |
| --- | --- |
| 编号 | ADR-009 |

## 2. 上下文（Context）

系统需要在统一模型、证据、知识与模板上提供检索（Agent 上下文构造、术语匹配、
对象检索），检索结果必须**按权限过滤**，且数据量与并发尚未证明需要独立搜索集群。
引入独立向量库或搜索引擎会增加运维面、私有部署复杂度与数据一致性问题。

上游 §2.2 裁定"PostgreSQL 是事实主库"；§2.3 否决"独立向量库集群"，仅在 pgvector
无法满足召回质量时才重新评估。

## 3. 决策（Decision）

1. 检索统一采用 **PostgreSQL 16 + pgvector**：全文检索使用 PostgreSQL 能力，
   向量检索使用 pgvector 扩展，与事实主库同源。
2. **首版不引入独立搜索集群（Elasticsearch/OpenSearch）与独立向量库（Milvus 等）**。
3. 检索必须做**权限过滤**：项目知识 / 公共知识分区，跨项目检索被拒绝，
   结果只返回调用者有权访问的对象。
4. Agent 检索只取任务所需片段，携带可引用 ID，遵循最小上下文原则（联动 ADR-005）。
5. Redis 只做短期缓存，不作为检索事实源。

## 4. 理由（Rationale）

- 数据量与检索需求未被证明需要独立集群，PostgreSQL 已能承担事务 + JSONB + 检索
  （§2.3 明确否决独立向量库集群）。
- 单一数据库减少运维与一致性负担，符合私有部署友好（§2.1 选型原则）。
- pgvector 与事实表同库，权限过滤可在同一事务/查询内完成，避免跨系统权限同步。

## 5. 后果（Consequences）

### 正面

- 部署栈更简单，少一套需要运维与调优的系统。
- 检索与权威数据同库，权限过滤一致、无跨系统同步延迟。
- 事务内可保证检索索引与写入一致。

### 负面

- 大规模向量检索的召回质量与吞吐受 pgvector 限制。
- 全文检索的高级相关性排序能力弱于专业搜索引擎。
- 向量索引构建与调优（HNSW/IVFFlat）需要额外关注。

### 风险

- 召回质量不足以支撑 Agent 结论。对策：固定金样例评估；触发条件出现时再评估独立向量库。
- 向量索引构建阻塞写入。对策：异步构建索引，写入链路不依赖实时索引。

## 6. 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 独立向量库集群（Milvus / Pinecone 等） | 数据量与检索需求未证明（§2.3） |
| Elasticsearch / OpenSearch | 引入第二套存储，一致性与运维成本高 |
| 图数据库（Neo4j）做关系检索 | PostgreSQL 已满足关系查询（§2.3） |
| 纯应用层内存检索 | 不可扩展、无持久化、权限过滤难保证 |
| 外部 SaaS 检索服务 | 私有部署不友好，数据外发不可控 |

## 7. 验证方式

1. 权限测试（M5-04）：跨项目检索被拒绝，公共/项目知识分区正确。
2. 金样例检索评估：固定查询集下召回与排序达到可接受标准。
3. 一致性测试：写入后检索索引与事实数据一致（异步索引最终一致可接受，需有测试）。
4. 性能测试：k6 在基准数据规模下测量检索延迟，与 M0 阈值对比。

## 8. 重新评估触发条件

- pgvector 无法满足召回质量（§2.3 的重新评估触发）。
- 跨项目图分析成为核心（对应 §2.3 Neo4j 触发）。
- 检索数据量或 QPS 使 PostgreSQL 成为瓶颈。
- 全文检索相关性成为影响使用的关键问题。
