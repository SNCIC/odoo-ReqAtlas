## 2. 上下文（Context）

2D 工作台需要节点/关系编辑、视口缩放、选择、泳道、自动布局等成熟交互能力。
候选库 `@xyflow/react`（React Flow）在这些交互上成熟，但它的数据模型是**面向展示的**
节点/边 JSON（含坐标、样式、句柄），与系统的语义模型（对象/关系/状态/来源）并非一一对应。

若把 React Flow JSON 直接持久化，将出现三类问题：语义与展示耦合、前端成为事实源、
客户视图与专业视图可能引用不同对象 ID（违反 P1）。上游 §2.2 与开发方案 §7.1 已裁定
"React Flow 只负责交互与坐标，节点/边语义来自 API"。

## 3. 决策（Decision）

1. React Flow **仅作视图适配层**，位于 `packages/canvas`，**不承载任何业务真相**。
2. 通过 **Domain ↔ React Flow Adapter** 双向转换：
   - Domain → React Flow：根据 ModelBundle 生成展示节点/边（含布局坐标）。
   - React Flow → Domain：编辑事件转换为 Command / ChangeOperation，**不直接持久化
     React Flow JSON**。
3. 节点/边的**语义字段来自 API**；React Flow 只管理交互状态与坐标。
4. 布局与语义分离：布局拖动在短时间窗口合并为 `ViewLayoutPatch` 单独保存；
   只有对象语义、关系、关键布局保存或显式保存才形成 revision。
5. 客户故事 2D 投影与专业视图**引用同一对象 ID**，不得各自生成 ID。

## 4. 理由（Rationale）

- 复用成熟交互能力，避免自研画布的高风险与高成本。
- 语义与展示解耦，使 2D、客户故事、3D 三视图语义一致成为可验证约束。
- 布局不写语义，避免高频拖动产生 revision 洪流（§4.4）。

## 5. 后果（Consequences）

### 正面

- 交互能力开箱即用，开发聚焦在语义适配与规则。
- 多视图一致性可自动化校验（对象 ID 一致）。
- 视图层可替换：更换画布库不影响领域模型。

### 负面

- 需要维护一层适配器，转换逻辑是新增的复杂度与 bug 面。
- 复杂自定义节点/边的性能受 React Flow 渲染机制约束（M0 需实测）。
- 布局与语义分离要求明确"何时算保存"，交互细节需产品确认。

### 风险

- 团队图省事直接持久化 React Flow JSON，破坏事实源（风险 R10）。对策：Adapter 层
  禁止直接调用写入 API，架构测试限制 `packages/canvas` 依赖。
- 高复杂度图的帧率/内存不达标。对策：M0-03 采集性能曲线，超阈值时评估虚拟化或分片。

## 6. 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 把 React Flow JSON 作为领域模型持久化 | 语义与展示耦合，前端成为事实源，违反 P1 |
| 自研画布引擎 | 交互/性能/可访问性成本高，偏离核心价值 |
| 直接使用 BPMN 建模库 | 超出首版范围（不做完整 BPMN 2.0），语义过重 |
| Canvas/WebGL 纯自绘 | 可访问性与编辑体验差，键盘不可达 |

## 7. 验证方式

1. 语义隔离测试：`packages/canvas` 的适配器单测，验证 Domain ↔ RF 转换幂等、
   且不产生持久化副作用。
2. 对象 ID 一致性测试（M3-07）：客户故事 2D 与专业 2D 视图对同一对象返回相同 ID。
3. 布局测试：连续拖动只产生 `ViewLayoutPatch`，`project_revision` 不变；
   显式保存后才 +1。
4. 架构测试：`packages/canvas` 不得导入服务端实现与直接写库模块。
5. 性能实测：M0-03 记录复杂度 → 帧率 / 长任务 / 内存 / 保存耗时曲线。

## 8. 重新评估触发条件

- 实测画布在目标复杂度下帧率或内存不达标（R1 相关）。
- 出现 React Flow 无法满足的核心交互（如大规模增量布局）。
- 客户视图与专业视图无法用同一对象 ID 表达。
- 布局合并策略造成语义与布局持续不一致的用户投诉。
