## 2. 上下文（Context）

首版由单人全栈维护，需要在本地一条命令启动、调试、迁移与测试，不依赖复杂云基础设施。
系统需要一个长驻的交互式编辑器（2D 画布与 3D 导览）、一组同步的语义读写 API，
以及若干耗时较长的异步任务（文档渲染、文件解析、索引、Agent 调用）。

当前没有证据表明存在需要独立伸缩或独立部署的服务边界：事件量、并发量、团队规模均
不足以支撑分布式复杂度。上游实施方案 §2.2 已裁定"TypeScript 模块化单体 + 独立
异步 Worker，不拆微服务"，本 ADR 将其固化为可执行约束。

约束条件：

- 领域规则必须可脱离框架测试（P1 唯一事实源、P2 写入单一入口）。
- 依赖方向由工具强制，不靠自觉（实施方案 §3.2）。
- 私有部署友好：核心链路可用容器在本机/私有机房运行。

## 3. 决策（Decision）

1. 采用**单仓（monorepo）pnpm workspace**，包含三应用与会话模块：
   `apps/web`（React SPA）、`apps/api`（NestJS + Fastify，模块化单体）、
   `apps/worker`（BullMQ workers）。
2. 领域逻辑集中在 `packages/domain`（entities / commands / validators / policies），
   **零框架依赖**，不依赖 NestJS、React、数据库驱动或模型 SDK。
3. 异步任务通过 Redis + BullMQ 投递，Worker 与 API 共享 `packages/domain` 与
   `packages/db`，但**只有 API 拥有同步写入入口**。
4. **首版不拆分微服务**，不引入服务网格、独立网关或跨进程事务。
5. 依赖方向由 ESLint `no-restricted-imports` 与 dependency-cruiser 架构测试强制。

## 4. 理由（Rationale）

- **单人可维护**：单一代码库、单一类型系统、单一部署单元，降低跨语言与跨进程调试成本。
- **迭代速度优先于理论伸缩性**：当前瓶颈是功能交付，不是吞吐（与 §2.3"Go 首版 API"
  否决理由一致）。
- **契约先行更易落地**：同一仓库内 OpenAPI 生成与前端客户端生成可在 CI 内完成无 diff 门禁。
- **领域可测试**：`domain` 无框架依赖使领域规则可用 Vitest 纯单测覆盖（P5 契约先行）。

## 5. 后果（Consequences）

### 正面

- 本地一键启动，私有部署仅需一套 Compose 栈。
- 领域代码可复用、可纯单测，重构成本低。
- 无需分布式事务与跨服务契约版本治理。

### 负面

- 模块边界依赖静态检查维持，缺少物理隔离的强制力。
- API 与 Worker 共享代码，耦合度高；重建 Worker 会牵动 API 代码。
- 以单一部署单元伸缩，长任务与短请求争用同一代码基（但进程可独立扩副本缓解）。

### 风险

- "顺手绕过"模块边界，跨模块直接访问对方数据表，污染唯一事实源（风险 R10）。
  对策：CI 架构测试 + 只读复核清单强制检查。

## 6. 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 微服务拆分（含 Kafka / 服务网格） | 事件量与并发未证明；分布式复杂度由单人承担不划算（§2.3 Kafka 项） |
| Next.js 全栈 | 编辑器是长驻 SPA，SSR 价值有限（§2.3） |
| Python 主后端 | 契约与单人维护需额外语言切换（§2.3） |
| Go 首版 API | 性能非当前瓶颈，迭代速度更关键（§2.3） |
| Serverless 函数 | 长驻编辑器与本地私有部署不契合，冷启动影响交互 |

## 7. 验证方式

1. 架构测试：`pnpm test:arch`（dependency-cruiser）对 "domain 不得依赖 Nest/React/DB 驱动"
   "禁止循环依赖" 规则返回 0 违规。
2. 启动验证：从干净环境执行 `pnpm dev:stack` + `pnpm dev`，web/api/worker 三者均
   通过健康检查。
3. 边界演练：临时在 `packages/domain` 引入 `@nestjs/common` 导入，架构测试必须**失败**，
   证明门禁有效。
4. 降级演练：停止 Redis 后 API 同步模型读写仍可用，仅拒绝新异步任务（§7.5）。

## 8. 重新评估触发条件

- 实测 API CPU 成为瓶颈（对应 §2.3"Go 首版 API"的重新评估触发）。
- 需要为某个模块独立伸缩或独立部署节奏。
- 团队扩张到多个小组各自拥有模块，模块边界需物理隔离。
- 出现必须跨进程事务或强隔离的合规要求。
