# ADR-007：身份与会话

| 项目 | 内容 |
| --- | --- |

## 2. 上下文（Context）

系统需要企业级身份认证与安全会话，且**不自研密码体系**。默认提供方 Keycloak，
但必须可替换为标准 OIDC 实现。浏览器侧不得持有可被脚本窃取的长期凭证。

上游 §2.2 与 §7.4 裁定：OIDC 校验 issuer / audience / nonce / state；会话由 BFF 管理，
浏览器只持 Secure + HttpOnly + SameSite Cookie；**token 不写 localStorage**；
CSRF 用 SameSite + CSRF token。

## 3. 决策（Decision）

1. 认证采用 **OIDC Authorization Code + PKCE**；默认提供方 Keycloak，可替换标准 OIDC。
2. **BFF（Backend-for-Frontend）管理模式**：`apps/api` 作为 BFF，持有 access/refresh
   token 并管理会话；浏览器只持有 Secure + HttpOnly + SameSite 的会话 Cookie。
3. **token 绝不写入 localStorage / sessionStorage**。
4. 服务端校验 token 的 `issuer` / `audience` / `nonce` / `state`；API 对所有请求校验。
5. CSRF 防护：SameSite + CSRF token 双重；退出、会话轮换、禁用用户均有明确行为。
6. 授权与应用分离：OIDC 只负责身份，租户角色 + 项目角色 + 对象分类由应用控制。
7. 会话相关安全用例（登录、退出、过期、禁用、CSRF、防开放重定向）纳入 M1 验收。

## 4. 理由（Rationale）

- 不自研密码体系，降低安全面（§7.4 控制项）。
- BFF 会话使浏览器不暴露 token，缓解 XSS 窃取风险，且便于服务端统一撤销会话。
- OIDC 标准可替换比绑定单一提供方更利于私有部署。
- 授权留在应用层，避免把业务权限模型塞进身份提供方。

## 5. 后果（Consequences）

### 正面

- 浏览器无长期凭证，XSS 窃取 token 的收益大幅降低。
- 会话可服务端集中撤销、轮换与审计。
- 提供方可替换，私有部署灵活。

### 负面

- BFF 增加 API 的会话管理职责与状态（会话存储），复杂度上升。
- 相比纯 token + localStorage，跨域与 Cookie 配置（SameSite、域名、Secure）更敏感。
- 需要额外处理 CSRF，前端请求须携带 CSRF token。

### 风险

- Cookie 配置错误导致 CSRF 或登录失败。对策：M1-03 安全用例全绿作为门禁。
- 开放重定向、错受众 token 被接受。对策：校验 `state` / `nonce` / `audience`，
  并纳入安全测试。

## 6. 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| token 存 localStorage | 可被 XSS 窃取，违反 §7.4 |
| 自研密码/会话体系 | 安全责任与合规成本高，无必要 |
| 纯隐式流（Implicit Flow） | 已不推荐，token 暴露在前端 |
| 仅用 OIDC 提供方做授权 | 业务权限模型（租户/项目/对象）需应用控制 |
| 绑定单一身份厂商 | 私有部署不友好，可替换性差 |

## 7. 验证方式

1. 安全用例（M1-03）：登录、退出、会话轮换、CSRF、防开放重定向、禁用用户全部通过。
2. token 检查：浏览器存储（localStorage / sessionStorage）中不存在 token；
   会话 Cookie 具备 Secure + HttpOnly + SameSite。
3. 伪造测试（§7.4）：校验 issuer / audience / nonce / state，伪造与错受众 token 被拒绝。
4. 越权矩阵（M2-03）：多角色访问控制测试通过。
5. 会话撤销：禁用用户后现有会话失效，需重新认证。

## 8. 重新评估触发条件

- 需要 SSO 目录同步（首版不做）导致会话模型需扩展。
- 部署形态变化要求无服务器端会话（纯 token），且能保证凭证安全。
- 客户要求对接非标准 OIDC 提供方而 PKCE/Code 流不兼容。
- 多域/多子域部署使 Cookie 策略无法安全落地。
