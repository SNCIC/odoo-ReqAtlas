本目录用**架构决策记录（Architecture Decision Record，ADR）**保存项目关键
技术裁定的上下文、理由、代价与退出条件。ADR 只记录"为什么这样定"，
不替代接口契约、数据迁移或任务清单。

---

## 1. 什么时候必须写 ADR

出现下列任一情形时，**必须先提交 ADR 再实施**，不得先落地再补文档：

| 触发情形 | 判定标准 |
| --- | --- |
| 影响跨模块边界 | 改变模块划分、依赖方向、应用与 Worker 职责 |
| 影响数据模型 | 改变事实源、版本链、隔离方式、迁移策略 |
| 影响部署形态 | 改变运行拓扑、容器编排、云厂商绑定 |
| 影响安全与会话 | 改变身份、授权、会话存储、密钥管理、数据外发策略 |
| 引入或替换第三方依赖 | 新框架、新数据库、新中间件、新模型供应商 |
| 冻结性能基线 | 阈值、目标设备、兼容矩阵的首次确定 |
| 推翻既有裁定 | 与已 Accepted 的 ADR 冲突，需要显式 Superseded |

不写 ADR 的情形：局部实现细节、命名与格式、可逆且无外部影响的小改。

---

## 2. 编号规则

- 采用 `ADR-NNN` 三段数字形式，从 `ADR-001` 起单调递增。
- 编号**一经分配永不复用**；被撤销的决策保留编号并标记状态，不回收。
- 文件名统一为 `ADR-NNN.md`，标题内数字与文件名一致。
- 无历史包袱的新决策一律取当前最大编号 +1；补写历史决策需在"上下文"中说明补记原因。

---

## 3. 状态机与状态变更责任人

```text
Proposed ──批准──> Accepted ──被新决策取代──> Superseded
```

| 状态 | 含义 | 允许操作 |
| --- | --- | --- |
| Proposed | 已起草，等待裁定 | 修改内容、附议、撤回 |
| Accepted | 已批准，作为实现依据 | 只读；内容修订须走新 ADR |
| Superseded | 已被新 ADR 取代 | 只读；注明取代者编号 |

- **状态变更责任人：总指挥**。开发者与顾问只提交 Proposed，无权自行置为 Accepted。
- 由 Proposed 转为 Accepted 需在"决策者"字段填写总指挥确认结果。
- 已被 Accepted 的 ADR **不得原地改写结论**；如需变更，新建一篇 ADR，将旧篇状态置为
  Superseded，并在两篇中互相引用编号。
- ADR 与实施方案冲突时：以上游文档为准，暂停实现并提交变更单裁定（见实施方案 §0.1）。

---

## 4. 单篇 ADR 的统一结构

每篇 ADR 依次包含：标题与元数据（编号 / 状态 / 日期 / 决策者）、上下文、
决策、理由、后果（正面 / 负面 / 风险）、被否决的替代方案、验证方式、
重新评估触发条件、关联章节。空白模板见 [template.md](./template.md)。
