# 行业知识包治理规范

> **版本**：v0.1　**发布日期**：2026-10-04　**状态**：`draft`
> **评审**：需实施专家评审（内容负责人中至少一名实施专家）
> **内容定位**：模板候选，需客户核实。行业知识包提供调研参照，**不是客户事实**。
>
> 依据：产品设计文档 §9.3 / 附录 E；开发方案 §6.5（M4-02）。

---

## 1. 目的与适用范围

本规范定义 `docs/knowledge/**` 下所有行业知识包的治理要求：谁能改、怎么评审、怎么发布、过期怎么办、项目反馈怎么回流。适用于所有行业包与其中的岗位话术库。

知识包的作用是让实施顾问在**进客户现场之前完成结构化预习**：看懂典型组织、核心流程、常见痛点、行业术语与控制点，从而问出内行问题、听懂客户黑话、识别异常回答。它**不提供客户事实**。

## 2. 知识边界（红线，不可协商）

1. 行业知识包提供**调研参照**，不是客户事实。
2. 套用模板后，所有角色、流程、痛点、合规提示、术语一律标为**「模板候选」**，必须经客户核实后方可升级为事实。
3. 任何模板内容不得直接进入基线；模板实例化产出的是 ChangeDraft（差异草案），不是已确认对象。
4. 合规内容仅作提醒，**需由相应专业人员确认**，不替代法律、税务或审计意见。
5. 项目确认后的客户事实**不反向污染**公共模板；匿名化经验须经知识管理员评审后才可沉淀（见 §7）。
6. 知识包内**不得出现**具体真实企业名称、人名、真实案例数据、客户合同条款原文或个人信息。

## 3. 治理字段定义

每个知识包必须声明以下字段（对应产品设计文档附录 E）：

| 字段 | 要求 | 通用贸易包取值 |
| --- | --- | --- |
| 名称与版本 | 语义化版本（`MAJOR.MINOR.PATCH`）并记录发布日期 | 通用贸易 v0.1（2026-10-04） |
| 适用范围 | 行业 / 细分场景 / 企业规模 | 通用贸易；内贸为主、含少量进出口；中小型企业 |
| 内容负责人 | 至少一名实施专家 | 实施专家（待指派）、内容负责人（待指派） |
| 评审状态 | 草稿 / 评审中 / 已发布 / 已废止 | `draft`（草稿） |
| 来源说明 | 公开依据或专家经验类型 | 公开通用业务惯例 + 实施经验归纳，未引用具体企业数据 |
| 有效期 | 到期触发复核，**不自动失效** | 12 个月，2027-10-04 触发复核提醒 |
| 变更日志 | 新增、修改、删除及理由 | 见每个文件末尾「变更日志」 |
| 项目反馈 | 候选改进，**匿名化且需评审** | 见 §7 |

### 3.1 版本号约定

- `MAJOR`：术语定义、流程骨架或合规要点发生**不兼容**变更（可能导致已确认对象失效）。
- `MINOR`：新增条目或补充说明，向后兼容。
- `PATCH`：文字订正、链接修复、错别字。

版本号与发布日期一并记录；发布记录见各文件「变更日志」。

### 3.2 评审状态机

| 状态 | 进入方式 | 允许动作 | 退出方向 |
| --- | --- | --- | --- |
| `draft`（草稿） | 内容负责人编写 | 编辑、补来源 | `reviewing` / `retired` |
| `reviewing`（评审中） | 提交评审 | 评论、修订、拒绝 | `published` / `draft` |
| `published`（已发布） | 实施专家评审通过 | 只读引用；改动须走新版本 | `reviewing` / `retired` |
| `retired`（已废止） | 被新版本替代或不再适用 | 只读留档，不再实例化 | — |

### 3.3 有效期与复核

- 有效期从发布日期起算（默认 12 个月）。
- 到期**触发复核提醒**，知识包**不自动失效**；复核可延长有效期、发布新版本或转 `retired`。
- 触发提前复核的情形：法规/税制调整、Odoo 主版本升级、多个项目反馈同一处错误。

## 4. 发布流程

1. 内容负责人完成初稿（`draft`），补齐来源说明与变更日志。
2. 指定至少一名实施专家评审；评审记录评审意见与结论（`reviewing`）。
3. 评审通过后由知识管理员发布，记录版本号与发布日期（`published`）。
4. 已发布内容只读引用；任何修改产出**新版本**，不原地覆盖。

### 5.1 知识包索引

| `package_id` | 名称 | 版本 | 日期 | 状态 | 确认 | 主目录 |
| --- | --- | --- | --- | --- | --- | --- |

## 6. 模板对象与 `template_origin`

- 模板包中的每条预置对象（角色、流程、单据、术语、痛点、控制点、问题卡）都携带 `template_origin`，用于溯源与「模板不反向污染」校验。
- 语义（见开发方案 M4-01）：

  | 字段 | 说明 |
  | --- | --- |
  | `package_id` | 知识包标识，如 `trade.generic` |
  | `package_version` | 实例化时的知识包版本，如 `0.1.0` |
  | `item_key` | 包内条目键，如 `role.sales` |
  | `instantiated_at` | 实例化时间 |

- 对象被实例化后**附带** `template_origin`，并默认状态为「模板候选」。客户核实、修改、删除后，该对象的来源状态转为客户事实，不得回写公共模板。
- 模板包中 `template_origin` 一律指向**本包自身**；跨包引用需显式声明。

## 7. 项目反馈流程

1. 顾问/实施人员在项目中记录候选改进（**须匿名化**：去掉企业名、人名、金额、单据号）。
2. 提交至知识管理员；管理员去重、归类，判断是否与既有条目冲突。
3. 涉及新增/修改条目的，走 §4 评审流程，产出新版本。
4. 反馈若包含未匿名化信息，**退回**直至匿名化完成；拒绝将单个客户事实直接写入公共模板。

## 8. 字段级模板候选标记约定

在知识包文件中，「模板候选」以两种方式呈现：

- 文件头声明：整个文件为模板候选。
- 逐条 `template_origin` 列：标注该条目的包内键与来源，便于结构化导入。
